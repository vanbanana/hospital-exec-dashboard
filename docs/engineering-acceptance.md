# 工程质量提升与验收计划（置顶）

> 项目约束：无法取得医院真实数据。目标是在确定性合成数据上达到可复现、可维护、可恢复的高工程质量。本文件定义后续工作，未完成项不能作为已有能力宣传。

## 1. 范围与评价原则

**不纳入验收**：取得真实医院数据、HIS/EMR/HRP 对接、与医院账单和真实临床结果对账、医院现场业务有效性验证。它们不再作为待用户提供材料的阻塞项，也不扣工程质量分。

**仍须验收**：合成数据的确定性、字段和单位正确性、指标勾稽、权限隔离、事务与并发、交互完整性、故障处理、部署、恢复、性能和依赖安全。数据可以合成，数据库、请求链路、权限和故障必须真实执行。

- 合成数据在 PostgreSQL 持久化，经 Go API 返回；运行中的前端禁止在接口失败后编造业务值。单元测试中的替身不受此限制。
- 固定种子版本、业务时钟、输入和预期结果。关键指标用独立的小型样本算出期望值，不能让同一段生产查询同时充当验收答案。
- 全部界面继续显示 `demo` 来源；安全配置中的“production”表示部署配置，不表示已获医院生产验收。
- 五级穿透、ChatBI、自动生成引擎等预留功能先决定是否纳入产品范围；未启用时不计为已完成。已展示的按钮、筛选器和状态必须有真实语义。
- 不以引入 Pinia、Redis、微服务或堆积测试数量评判质量。以行为、边界和可复现证据评判。

## 2. 按顺序执行的计划

| 顺序 | 工作 | 完成条件 | 当前状态 |
| --- | --- | --- | --- |
| D0 | 文档与范围对齐 | 端点、页面、配置、命令与实现一致；实际结果与能力规格分开；移除真实数据前置条件 | 页面、路由、迁移与配置清单按源码核对；不提供开发时间线 |
| E1 | 契约、权限与业务闭环 | 下面 §3 的接口矩阵和独立样本断言通过，事务失败和并发竞争有证据 | 认证、工单事务和范围控制已有实现；完整逐端点矩阵须独立验收 |
| E2 | 页面与交互可靠性 | 下面 §4 的实际交互与五态检查通过，未知路由和无效筛选修复 | 未知路由回退、固定口径和偏好已实现；完整五态与键盘交互须验收 |
| E3 | 恢复与运维 | 非空业务写入恢复后内容一致；记录恢复耗时，建立自动备份及失败告警 | 备份、内容恢复校验和调度工具已提供；目标主机激活、故障及恢复须验收 |
| E4 | 可复现交付 | 干净检出、初始化、升级、HTTPS 浏览器检查和托管 CI 有可追溯结果 | 锁文件、初始化、迁移及 HTTPS 配置已提供；托管 CI 与接收方部署须验收 |
| E5 | 容量、性能与持续安全 | 固定负载下延迟、错误率、资源与恢复满足预先确定的目标；依赖与镜像扫描有结果 | 认证负载、指标、索引及日汇总已实现；持续读写容量、首屏预算和扫描须验收 |

执行时每完成一个阶段，把代码版本、命令、输入、输出、失败项及未测项按 [维护要求](quality-remediation-plan.md) 保存独立验收报告。已有修复不代表所有高标准已经通过。

## 3. E1：契约、权限与业务闭环

1. 以 [现状端点清单](current-state.md) 建立逐端点矩阵：方法、请求、成功、空集合、null、非法字段、错误方法、未认证和禁止角色。关闭仿真时确认五个端点不注册，并考虑认证中间件先返回 401 的情形。
2. 用小型合成样本检查金额元/万元转换、率值 0~1 与展示百分数、合计/分项、跨页面同指标同口径、分页 `total` 和过滤结果一致、时间边界及分母为零。规模合理的 ±10% 容差不能替代相同口径下应成立的精确恒等式。
3. 明确 `all/domain/dept` 各角色的数据范围契约。当前未定义的 domain 聚合继续拒绝；科室统计若纳入范围，用合成样本实现与验证，不能等待真实医院数据。记录未知角色、停用账号、过期/吊销会话和跨科室访问结果。
4. 告警认领、派发、接单、办结、关闭分别验证合法状态迁移、非法迁移、重复提交、截止时间、并发抢单与失败回滚；工单、告警和审计的一致性必须能查证。记录现有重复提交返回冲突的语义，不把它宣传为幂等成功。
5. 确认“办结工单”只改变业务状态；指标恢复须有单独的合成场景或派生实现。登录锁定、滑动续期、个人偏好所有权与强制脱敏在独立样本上验证。
6. 验证 Cookie、同源写入、跨站请求、响应头、请求体上限和代理 IP 边界；覆盖未授权请求和非 JSON 网关错误。未有证据前不声称通过全面安全审计。

## 4. E2：页面与交互可靠性

1. 对 14 个导航页面、无权限回退页、登录和大屏分别检查加载、空、错误、陈旧数据、重试；按钮、表单、分页、筛选、金额展示和声音实际操作。
2. 回归根级未知路径回退与科研、患者、质量、资产页的固定统计口径；这些页面已移除无效时间筛选，不得重新引入不对 API 生效的控件。
3. 验证偏好保存失败回滚、刷新后持久化、身份切换清态、拒绝页面导航和吊销会话跳转；系统设置的数据源列表明确是合成登记，不暗示连接医院系统。
4. 模拟 30 秒超时、慢响应、请求乱序、断网再连接、轮询期间离开页面，检查重复请求、定时器与 ECharts 释放。大屏现有手动重试及 30 秒轮询分别验证。
5. 按目标桌面尺寸、窄屏和键盘操作检查布局、焦点、表单标签、禁用状态及可读提示。页面冒烟不能代替这些检查。

## 5. E3：恢复与运维

1. 在隔离库生成非空工单、告警状态变化、个人偏好和审计，再备份恢复到新库；检查业务表内容摘要、主外键、序列后续写入、迁移台账和 API 关键结果。
2. 非空副本恢复后比较全部业务表及序列，并通过真实 API 验证读写。
3. 记录备份时间、备份对应的数据时点、恢复耗时与恢复验证耗时；先制定备份频率及 RPO/RTO 目标，再演练评判。恢复目标须提前约定，实测结果不等于故障时的数据丢失保证。
4. 增加自动备份、保留策略、备份失败告警和定期恢复演练；备份权限、拒绝覆盖及恢复限新库保持有效。
5. 检查数据库中断、磁盘满、连接池耗尽、应用重启、优雅停机和升级中断。`ready`、日志、外部告警与操作手册必须能对应故障；单机 Compose 不计为高可用。

## 6. E4：可复现交付

- 从干净检出使用锁文件安装，记录 Node/Go/PG 与镜像版本；不依赖外部临时编排文件完成初始化。
- 分别验证基础演示配置和生产安全配置；生产配置在已初始化的合成数据副本上执行，仍显示 `demo`。
- 将配置检查、浏览器权限检查与实际 HTTPS/Secure Cookie 检查区分。现有 CI 的权限浏览器阶段使用 HTTP，尚不覆盖真实 TLS 行为。
- 增加文档与路由/迁移/配置的漂移检查；托管 Actions 要有实际运行结果，当前只有本地执行证据。
- 保留迁移重跑不重播种、命名卷持久化和升级失败恢复证据；配置、部署及进程启动分别验证。

## 7. E5：性能与持续安全

- 负载须包含认证后的业务查询、分页、写操作与重型大屏，而非仅 `/health` 和匿名大屏。记录硬件、数据规模、并发、缓存状态、持续时间和失败请求。
- 建立基线后，在修复前固定目标 RPS、p95/p99、错误率、CPU/内存和连接池上限，持续至少 30 分钟检查稳定性及降载后恢复。Go `-race` 通过不等于容量测试通过。
- 分析慢查询和 `EXPLAIN`，验证索引、分页和并发写锁；对比修复前后相同输入的结果与资源消耗。
- 为首屏、图表分包和交互制定包体与耗时预算；现有 ECharts 体积提示保留，按实际加载测量决定优化。
- 定期执行 npm、Go、容器系统包扫描并保存版本与公告处置；分别记录可达、不可达、未修复和误报。现有 npm/govulncheck 结果不能代表容器系统包或未来版本安全。

## 8. 完成定义

每个阶段只有在约定行为、异常边界和复现命令都有证据后才能改为完成。报告统一写“通过 / 未通过 / 未验证”，不以代码量、测试数量或合成数据看起来逼真代替验收。

即使所有工程门禁通过，也只证明本项目在声明的合成数据、部署规模和负载范围内达到相应工程标准。

运维与性能实现规格和操作入口见 [operations-performance.md](operations-performance.md)。完整 E1–E5 清单须逐项验收；验证入口与限制见 [验证范围](quality8-evidence.md)。
